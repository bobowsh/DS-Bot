# DSH Profile 插件运维

## 安装与升级

- 使用 DSH 自带的 profile 插件命令管理安装，不要直接对 profile 目录执行裸 `pnpm add`；前者会应用宿主的供应链策略和工作区处理。
- 固定精确版本执行安装或升级，避免意外引入 latest 的破坏性变化。
- 先备份 profile 的 `package.json`、锁文件和实际生效的 `cordis.patch.yml`，并记录目标插件当前版本；准备可执行的回滚命令。
- 升级前核对插件的 peerDependencies 是否满足宿主内置 DSH 包与 Cordis 版本；不要用 `--force` 或 `--legacy-peer-deps` 绕过真实冲突。
- 若出现 `ERR_PNPM_NO_OFFLINE_META`、bundle-in-use 或 management-required，停止并查明上下文，不要继续强装。
- 多个插件连续修改同一 profile 时，每次修改后重新读取 `package.json`、锁文件和 patch，再进行下一次；否则可能覆盖前一次结果。
- 对正在运行的插件执行升级前，判断更新是否会中断当前会话；未经用户确认不要重启宿主。

## Patch 与能力挂载

- 区分用户级 patch、profile 级 patch 和插件包自带 patch；它们不是同一层，验证与备份时必须明确实际生效层。
- 修改 MCP 的 `serverName` 前检查全局和所有 Bot 能力中是否已存在同名项；若存在，应原子地完成“创建能力、挂载目标 Bot、关闭全局来源”，避免启动时冲突。
- 不用普通文件复制直接覆盖正在被宿主维护的 `state.json`；宿主可能在下次保存时整份回写，覆盖手工修改。
- 能力变更应走宿主提供的管理端点，并读取实际响应和保存后的状态；确认目标 Bot 已挂载、非目标 Bot 未挂载。
- 启动期 patch 不会因修改配置立即生效。没有获准重启时，只交付重启后的验证清单，不声称运行时已验证。

## 验证清单

- 读取已安装包的 `package.json`，确认版本与要求一致。
- 确认新增文件、依赖和入口存在，并记录实际文件大小或可执行输出。
- 比较安装前后的 patch 内容；无变化时明确说明，不要只说“未发现问题”。
- 检查锁文件确实解析到目标版本和新增依赖。
- 若界面提示更新失败，但磁盘、依赖、锁文件和 patch 均一致，应区分“旧更新流程失败”与“当前安装不完整”，并给出时间与证据。
- 涉及工具可见性时，在获准重启后分别检查目标 Bot 和非目标 Bot 的会话工具列表；重启前不得宣称工具已正确隔离。
- 最终报告区分：已安装、已配置、已静态验证、尚待运行时验证，并明确是否重启宿主。
