## 四、特别核对：上游 0.3.5 的群 ledger 重写

上游 0.3.5 有一批「message-ledger」提交（`db2cbf7c`、`9538c710`、`c71dade8`、`a9cf84a9` 等），把群消息改成**账本（ledger）存储**，`ds-bot/src/host/groups.js` 一个文件改了 **1,043 行**。

**它会不会让我们刚做的群聊渲染冲突或失效？——会冲突，但冲突面很小，而且不影响我们的做法。**

证据（实测对比 `v0.3.6` 与 `gh/dev` 的 `GroupReplies`）：

- **上游 0.3.6 的 `GroupReplies` 与我们的几乎一样**：都从 `actions.roomProgress(sessionId)` 拿 `{ replies, speaking }`，都靠 `stackReplies` 画成员气泡，都画「正在输入」提示。
- **上游多了一段**：结算后按 `relayRange(resultText)` 定位到账本里的行号区间，再调 `actions.groupRows(sessionId, from, to, anchor)` 把那段读回来（配合它新的 ledger 存法）。
- **我们没有那段**——我们靠 `parseReplies(contentText(content))` 从调用结果里解析回复。

所以冲突块只有 1 处（就是 `settledRows` 那段注释与实现的上游新增），**形态2 的核心（不占 tool-call 座位、团队工具注册进 `tool.call.toolview`、群聊不派发普通工具、成员回复原地画、状态行只在单聊画）全在上游没碰过的代码路径上，不受影响**。

**但有一个必须由人判断的点**：上游 ledger 改了群消息的**存储与取回方式**（`groups.js` 1043 行、`parts.js` 173 行、`channel.js` 129 行），我们的**群历史补录**功能也建立在这套之上。合完必须实测：
1. 群里成员回复能不能正常显示（ledger 存的历史）；
2. 群历史补录（翻旧页）还能不能读到旧消息；
3. 「正在输入」提示在 ledger 模式下还准不准。

## 五、推荐合并基线

**推荐：只并 `v0.3.6`（main 的发布版），不并 `up/dev`。**

理由：
- `up/dev` 是上游的开发分支，含未发布的改动（`git log up/dev` 里有大量非 release 提交），并进来风险不可控；
- 用户要的是「合并上游最新版本」= 最新的**发布版**；
- `up/dev` 留作以后再说。

**合并方式**：`git merge v0.3.6` 到 `dev`（走 PR，不直接提交到 dev）。

## 六、合并步骤（待批准后执行）

1. `git fetch up` → 确认 `v0.3.6` 指向 `a66cc737`。

   - **两边都要的**：依赖版本（`package.json` 取上游新版本 + 保留我们的定制）、i18n 文案表（两边条目合并）。
4. `ds-bot/src/client/` 改完后跑 `npm run build` 重建 `client.js`（那 64 个冲突块自动消失）。

   - 群聊：成员回复 + 提示 + 无工具明细 + 无状态行；
   - 群历史补录：翻到旧页，旧消息读得到；
   - 单聊：宿主原生工具行 + 状态行。
7. 出 PR（base `dev`），中文正文含冲突处置说明与 CDP 证据。
8. 重新构建安装包并校验。

## 七、必须由用户/队长拍板的取舍点

1. **上游 0.3.5 的手机端（`mobile/`）要不要一起进？** 上游新增 `mobile/src/team/*`、`mobile/src/ui/*` 等约 30 个文件。我们桌面应用用不到，但 `up/dev` 里有 `dsh-client-ui-git-graph` 之类可能依赖。**建议：不引入手机端文件**，但要看 `ds-bot/package.json` 的依赖有没有因此变化。
2. **上游的「记忆分层」（`2026-11-09-memory-layers.md`）会不会两套并存打架？** **已盘清（2026-11-14）：不会。** 见 7.1。
3. **上游新增的 `app/src/office-patch.mjs` / `release-notes.mjs`**：我们已有同名的 `office-patch.mjs`（我们的是从上游改的）。**以谁为准？** 我倾向保留我们的实现、上游的不要。
4. **上游 `agent-new.js`**（`singleFlight`、`agentSessionToReuse`）与我们 0.3.2 的会话复用逻辑不同，这块上游是新增能力，**是否要**？建议不引，除非它修了我们遇到的问题。

## 7.1 记忆分层：已盘清，不会两套并存

实测对比 `gh/dev` 与 `up/main` 的全部记忆文件：

```
ds-bot/src/host/memory*.js、ds-bot/src/client/memory-panel.js
ds-bot/test/memory*.test.js
```

**文件清单完全一致**（我们这 8 个 + 3 个测试文件，上游一个不多一个不少），**逐文件 diff 只有 `memory.js` 一个文件有差异**：+69 / −15 行。

看差异内容，我们与上游**是同源**的（`memory-entries.js` / `memory-pending.js` / `memory-search.js` / `memory-tidy.js` / `memory-review.js` / `memory-copy.js` / `memory-panel.js` **逐字节相同**），上游这期间在 `memory.js` 上补的是：

| 上游新增 | 性质 | 建议 |
|---|---|---|
| `memoryEdit` / `memoryAdd` 两个 API（用户直接改/加记忆条目，走移动端面板） | **纯新增**，走 `rt.memoryEndpoint` 一类的宿主接口 | **以我们为准**，不引（我们没有移动端面板，引入是死代码） |
| 摘要调用的 token 预算从 2,048 / 8,192 提到 16,384 / 32,768 | **纯参数调整**，解决「思考模型把输出预算全花在 reasoning 上」 | **以我们为准**，但**值得记一笔**：这是上游修的实测 bug，我们的摘要调用同样会踩（我们的 `SUMMARY_MAX_TOKENS` 仍是 2,048）。合并时建议**只把这两个常量提上去**，其余不动 |
| `assembleLlmStream` + `EMPTY_RESPONSE` / 502 的重试 | 与记忆无关，属上游 LLM 层的通用改动 | 合则合，与记忆无冲突 |

**结论：记忆这条线没有实质冲突**，最多是 `memory.js` 一个文件的 1 个冲突块（两边都改过同一段摘要调用代码），逐块看即可。**不是「两套并存打架」的风险点**，第七节第 2 点就此关闭。
