# #12 出厂插件与技能自动更新 · 验收测试说明

> 结构：**用户故事** → 每条故事拆成 **EARS 场景**（泛用 / 事件驱动 / 状态驱动 / 异常处理 / 可选特性）
> 每个场景给四项：**造数据 → 触发 → 观测点 → PASS 判据**
> 标注「替代验证」的，说明为什么不能走真实路径。

---

## 故事 1：内网运维，装完就不管了

> **作为**内网装机的人，
> **我希望**装好之后插件和技能能自己更新、我什么都不用点，
> **以便**机器不会停在出厂那天的版本。

### S1.1【事件驱动】22:00 自动更新

- **当** app 在运行、时间已过 22:00、且当日尚未检查过时，系统**应**依次触发插件通道与技能通道的检查，自动下载并落盘。
- 造数据：Gitea 给某插件打一个新 tag 并登记进 catalog；SkillHub 给某技能发一个新版本。
- 触发：改 `factory-update.json` 里的当日标记（或直接把系统时间改到 22:01）。
- 观测点：`<data>\logs\factory-update.log` 应有该插件的更新记录；`profiles/ds-bot/node_modules/<插件>/package.json` 的 version 变了。
- PASS 判据：日志出现 `plugin <名> updated to <新版本>`；磁盘上 version 字段 = catalog 声明的新版本。

### S1.2【事件驱动】装完提示重启

- **当** 一次更新装完之后，系统**应**在窗口出现时提示「已更新 N 项，重启生效」。
- 造数据：同上，制造至少 1 项更新。
- 触发：重启 app（走 `tellPluginsUpdated` 那条路径）。
- 观测点：界面弹窗；`start/text.mjs` 里的 `dialog.plugin.updated` 文案。
- PASS 判据：弹窗文案出现「N 个插件已经更新」且 N ≥ 1。

### S1.3【状态驱动】当日不重复检查

- **在** 当天已经检查过一次的状态下，系统**应**不再重复检查，直到次日。
- 造数据：`factory-update.json` 里 `day` = 今天。
- 触发：再次重启 app 或等下一个小时 tick。
- 观测点：日志无新的检查记录。
- PASS 判据：日志出现 `already checked today`（或等价文案）。

### S1.4【状态驱动】错过 22:00 不补查

- **在** 时间已过 22:00、但当天未跑检查的情况下，**如果** 用户此时关闭 app，**那么**系统**应**不补查，等次日 22:00。
- 说明：这条是 Q4 已拍板的语义（不补查、只认当天 22:00）。
- 造数据：`factory-update.json` 清空当日标记。
- 触发：在**非** 22:00 后的时间点启动 app（或把时间设到 22:00 之前）。
- 观测点：日志无检查记录。
- PASS 判据：启动后日志没有 check 记录。
- ⚠ **与 issue 原文有冲突**：issue 的「22:00 触发器」一节写「错过等下次开 app 补查」，而 Q4 决策写「不补查」。**这条要用户拍板以哪个为准**。

## 故事 2：catalog 能上新、也能下架

> **作为**内网的插件维护者，
> **我希望**在 catalog 里加一条就自动装、删一条就只是停更，
> **以便**上新和下线都不用重新打包分发。

### S2.1【可选特性】新增条目自动装并启用

- **在** catalog 新增了一个条目的情况下，系统**应**自动下载安装，**并**写入 profile manifest 的 `dependencies` 与 `dsh.profile.bundles`。
- 造数据：catalog `plugins.json` 加一条（npm 包已发布到内网 registry）。
- 触发：清当日标记后跑更新。
- 观测点：`profiles/ds-bot/package.json` 的 `dependencies` 有该项；同一文件 `dsh.profile.bundles` 有该项；`node_modules/<插件>/` 存在。
- PASS 判据：两处字段都在，且磁盘目录存在，且 DSH 重启后该插件生效。

### S2.2【状态驱动】禁用过的只升文件不写回 bundles

- **在** 某插件已被用户禁用（bundles 里没有它）的状态下，系统**应**只升级文件，**不应**把它写回 bundles。
- 造数据：从 `dsh.profile.bundles` 手工删掉该插件，保留 `dependencies` 与 `node_modules`。
- 触发：该插件的新版本进 catalog 后跑更新。
- 观测点：`node_modules/<插件>/package.json` version 变了；`bundles` 里**仍然没有**该项。
- PASS 判据：version 升级 ✅ 且 bundles 不含该插件 ✅。

### S2.3【可选特性】删除条目只停更不卸载

- **在** catalog 删除了一个条目的情况下，系统**应**只停止更新，**不应**卸载已安装的插件。
- 造数据：从 `plugins.json` 删掉一条。
- 触发：跑更新。
- 观测点：`node_modules/<插件>/` 仍在；结果里该插件出现在 `leftAlone`。
- PASS 判据：目录存在、文件未被删。

## 故事 3：装坏了要能退回去

> **作为**内网装机的人，
> **我希望**更新失败时机器保持可用，
> **以便**一次坏包不会把整台机器搞坏。

### S3.1【异常处理】源不可达

- **如果** catalog 不可达或 tarball 下载失败，**那么**系统**应**保留旧版不动、记失败，并在次日重试。
- 造数据：把 `CATALOG_URL` 指向一个死端口（或用进程级死端口代理）。
- 触发：跑更新。
- 观测点：`node_modules/<插件>` 的 version 未变；日志有失败记录。
- PASS 判据：version 不变 + 日志有 error。

### S3.2【异常处理】归档版本不符

- **如果** 归档声明的版本与 catalog 声明的不一致，**那么**系统**应**拒绝并保留旧版。
- 造数据：造一个 version 字段与 catalog 不符的 tarball。
- 触发：跑更新。
- 观测点：日志文案 `the archive carries X, not Y`。
- PASS 判据：该文案出现，version 未变。

### S3.3【异常处理】换入失败回滚

- **如果** 解包或换入失败，**那么**系统**应**把旧版移回原位，不留半成品。
- 造数据：给一个坏 zip / 让 rename 失败。
- 触发：跑更新。
- 观测点：旧目录内容逐字节不变（SHA256 指纹对比）；`skills-update-staging/` 与 `skills-update-backup/` 无残留。
- PASS 判据：指纹与更新前一致 + 两个临时目录为空。

### S3.4【异常处理】兼容熔断（Q6）

- **如果** 归档声明的 `engines.dsh` 与本机 DSH 版本不匹配，**那么**系统**应**跳过该条目（记 `skipped`，次日再看），**不应**计入连败。
- 造数据：造一个 `engines.dsh` 要求不存在版本的 tarball。
- 触发：跑更新。
- 观测点：结果里该插件在 `skipped` 而不是 `failed`；`factory-update.json` 的 `failures` 里**没有**它。
- PASS 判据：`skipped` 命中 + `failures` 无该项。

### S3.5【异常处理】失败熔断（Q7）

- **如果** 同一版本连续失败 3 次，**那么**系统**应**当天不再尝试。
- 造数据：让同一插件的下载持续失败。
- 触发：连续跑 3 次更新。
- 观测点：`factory-update.json` 的 `failures[名]` = 3；第 4 次不再尝试。
- PASS 判据：计数到 3 后不再发起请求。

### S3.6【异常处理】无 dsh 清单拒收

- **如果** 归档不带 `dsh` 清单，**那么**系统**应**拒收。
- 造数据：造一个没有 `dsh` 字段的 tarball。
- 观测点：日志 `does not declare itself a DSH plugin`。
- PASS 判据：该文案出现，旧版保留。

### S3.7【异常处理】未预批的构建脚本拒收

- **如果** 归档带 install 脚本、且该包不在出厂清单上，**那么**系统**应**拒收。
- 造数据：造一个带 `postinstall` 的 tarball，包名不在 `data/factory/plugins.json`。
- 观测点：日志 `carries install scripts (...) and is not on ...`。
- PASS 判据：该文案出现，未安装。

## 故事 4：技能也走同一条路

> **作为**内网装机的人，
> **我希望**技能和插件一样能自动更新，而且我自己改过的技能不被冲掉，
> **以便**既有新版用，又不丢本地改动。

### S4.1【可选特性】技能有新版时自动落盘

- **在** SkillHub 上某技能发布了新版本的情况下，系统**应**下载并覆盖本地副本。
- 造数据：用 CLI 给 `grilling` 发一个新版本。
- 触发：跑技能 sync（每小时一次，或直接调）。
- 观测点：`skills-repo/grilling/` 内容变化；`skills-sync.json` 的 `versions.grilling` = 新版号。
- PASS 判据：文件内容变了 + 版本记录更新。

### S4.2【状态驱动】首次只记录不覆盖

- **在** 某技能在 `skills-sync.json` 里没有记录的状态下，系统**应**只记录版本、不下载覆盖。
- 造数据：从 `skills-sync.json` 删掉该 slug。
- 触发：跑 sync。
- 观测点：结果里在 `recorded` 而不是 `updated`；目录内容不变。
- PASS 判据：`recorded` 命中 + 目录指纹不变。

### S4.3【可选特性】SkillHub 不认识的 slug 不动

- **在** 本地 skills-repo 有某目录、但 SkillHub 上没有该 slug 的情况下，系统**应**保持原样。
- 造数据：本地加一个 SkillHub 没有的目录（带 SKILL.md）。
- 触发：跑 sync。
- 观测点：该目录内容不变，结果里不出现。
- PASS 判据：指纹不变。

### S4.4【泛用】装机端不出外网

- 系统**应**只访问内网 Gitea 与内网 SkillHub，不发起任何外网请求。
- 造数据：无。
- 触发：完整跑一轮更新。
- 观测点：抓包或用死端口代理验证外网不可达时功能仍正常。
- PASS 判据：外网被阻断时，内网更新仍成功。

### S4.5【异常处理】技能解包失败回滚

- **如果** 技能包解包失败，**那么**系统**应**保留本地旧版、清掉暂存与备份。
- 造数据：让 zip 损坏。
- 观测点：`skills-repo/<slug>/` 内容逐字节不变。
- PASS 判据：指纹不变 + 无 staging/backup 残留。

## 已知限制与替代验证

1. **无法真等到 22:00**：用「改 `factory-update.json` 当日标记 + 直接调 `updateFactoryPlugins`」替代。这是**替代验证**，真实路径（等 22:00 自然触发）**未验证**。
2. **无法验证「重启后版本已升」的完整链路**：需要打真包、装到干净机器上跑。开发机只能验证到「磁盘上 version 字段已变」。
3. **断网**：用进程级死端口代理（`HTTPS_PROXY=http://127.0.0.1:1`）注入被测进程，不碰系统网络配置。
4. **S1.4 与 issue 原文冲突**：Q4 写「不补查」，issue 的 22:00 触发器一节写「错过等下次开 app 补查」。**需用户拍板**。

## 验收结论口径

| 结果 | 含义 |
|---|---|
| PASS | 有真实输出/截图/文件比对作证 |
| FAIL | 实测不符，附实际与期望 |
| BLOCKED | 缺前置条件，写明解除条件 |
| **不写 = 未验证** | 没跑就不能写 PASS |
